# 夸一夸小程序 · 产品需求稿 v0.1

日期：2026-09-28  
状态：需求与交互方案；尚未实现小程序、服务端或真实 AI 接入。  
本次交付：独立项目需求稿、分类提示词草案、账号知识库边界、首期验收口径。

> 当前产品评审入口：[产品方案 v1.0](../../产品方案-v1.0.md)。后续用户已确认五类同等投入、知识由用户确认后积累、首期加入限次数包月套餐；涉及这些范围和优先级，以产品方案为准。海报生成总提示词、五类差异化规则及图片处理流程以产品方案第六节为唯一维护入口。本稿其余部分保留为补充需求，不能沿用下文旧的“收费方式待定”将套餐排除首期。

## 1. 问题与目标（Problem Statement）

用户希望用照片和一句话，把日常经历变成有针对性、值得分享的夸夸海报。输入过程需要简单，回应需要贴近本人和当前经历，不能只是换称呼的通用赞美。

本轮用户明确：

- 夸一夸单独立项，后续做成小程序。
- 保留宝妈、职场人、学生、长辈、日常分类；不同分类使用不同提示词。
- 上传照片和一句话直接生成可保存、可分享的海报。
- 暂不设置珍藏和底部导航；可保留制作记录入口。
- 每个账号有自己的个人知识库，记录用户及家人的经历、偏好，让夸赞更懂本人；本轮已确认不是商家知识库。

当前已认可的视觉方向见 [效果图](../../../design/approved-concept-2026-09-28.png)。效果图只作为视觉参考，不等于已经实现；本稿新增的账号、知识库与制作状态页面尚无新版效果图。

## 2. 产品方案（Solution）

### 2.1 首期产品结构

前台保持两步主流程：选分类、上传照片、写一句话 → 查看海报、保存或分享。账号知识库与生成任务在后台支持这个流程，不强迫用户先录入完整资料。

| 页面或入口 | 首期行为 |
|---|---|
| 首页／创作页 | 分类标签、照片区域、一句话输入、生成按钮；右上角提供轻量“我的”入口，不设底部导航 |
| 制作状态页 | 显示真实制作状态，允许离开；失败可重试；已提交的照片和文字不丢失 |
| 海报结果页 | 展示最终海报、保存图片、分享；可返回修改输入重新生成 |
| 我的 | 制作记录、关于我／我的资料、账号设置与反馈 |
| 制作记录 | 制作中、失败、已完成记录；查看详情、重试、删除；不另建珍藏体系 |
| 关于我／我的资料 | 用户可理解的个人知识库入口，管理本人／家人、经历、表达偏好与使用范围 |

“我的”替换效果图右上角的“记录”是本次建议，方便同时承载记录和知识库；不扩展为重型个人中心。若继续保留“记录”，可在记录页内提供资料入口。

### 2.2 首页规则

- 分类不是永久身份，用户每次可切换；示例图选中宝妈不代表所有新用户默认宝妈。
- 建议新账号默认“日常”，老账号记住上次选择；切换分类保留照片与输入。
- 沿用已有需求，支持 1–6 张照片与非空配文；默认界面突出一张照片，追加照片使用轻量加号。
- 分类只改变回应策略和输入提示，不弹出额外问卷。
- 可先编辑草稿，在第一次提交服务端制作前完成账号识别；失败或取消登录应保留输入。账号识别不要求手机号作为首期前提。
- 知识库为空时也能直接生成。
- 输入长度、图片大小等上限须在实现前统一配置与展示；本稿不将效果图中的示例数值当成已确认规则。

### 2.3 分类策略

| 分类 ID | 显示名 | 重点回应 | 配文提示示例 | 避免 |
|---|---|---|---|---|
| parent | 宝妈 | 当前记录里的陪伴、孩子的小进步、照顾者自身感受 | 今天和孩子发生了什么？ | 默认母亲必须牺牲；只夸孩子；凭照片推断亲属关系或年龄 |
| work | 职场人 | 具体行动、推进、学习与阶段完成 | 今天哪件事值得给自己一个肯定？ | 美化过劳；把一次成果说成升职加薪；带入未提供的公司信息 |
| student | 学生 | 尝试、理解、坚持与探索 | 今天有什么小进步？ | 分数至上；比较其他学生；保证考试结果 |
| elder | 长辈 | 兴趣、新体验、自主选择与生活乐趣 | 今天有什么开心或新鲜的事？ | 居高临下；“这么大年纪还…”；根据外貌判断健康或年龄 |
| daily | 日常 | 普通生活的具体细节与愉悦 | 这一刻，你想留下什么？ | 空泛口号；编造照片故事；所有场景使用同一鸡汤 |

### 2.4 生成策略与成果

生成使用：平台通用规则 + 本次分类已发布提示词 + 本账号允许使用且相关的知识条目 + 本次照片与配文。

当前生成流程：服务端验证账号与输入 → 创建任务并固定提示词版本 → 检索本账号允许使用的相关知识 → 逐图理解并生成对应夸赞 → 校验事实与格式 → 处理图片 → 设计并合成一张 3:2 横版海报 → 检查成品 → 标记完成。具体模板和验收以[产品方案第六节](../../产品方案-v1.0.md)为准。

- 先处理照片的主体、背景、曝光与色调，再按内容安排主图和辅助图；保留人物身份、动作及重要物件，不机械套用等大格子。每张照片分别对应夸赞，合成一张横版海报。智能图像处理尚未在网页原型接入。
- 文案阶段输出标题与逐图夸赞列表，按照片编号保持对应。合成阶段使用已校验文字，必要时通过受控排版保证清晰中文；不把模型输出直接当成任意可执行 HTML。
- 内容重心是用户这次经历。知识库仅补充有关背景，不强行炫耀“我记得你”。
- 负面情绪先回应感受，不强行劝乐观，不把疲惫包装为必须继续付出。
- 只基于用户提供或已确认的事实，不从照片推断身份、亲属关系、健康等背景。
- 当前配文与旧资料冲突时，以本次明确表达为准，跳过冲突旧资料，不自动覆盖知识库。
- 海报预览是用户分享前的最终可见内容；知识库原文、内部条目 ID 与调试信息不进入导出海报。

## 3. 用户故事（User Stories）

1. 作为新用户，我不填写资料也能用照片和一句话完成首次制作。
2. 作为不同场景的记录者，我可以切换分类，保留已经输入的内容。
3. 作为已有账号的用户，我希望被允许使用的历史背景帮助 AI 更懂这次经历。
4. 作为用户，我能查看、更改、停用、删除自己的知识条目，而不是被系统固定标签。
5. 作为用户，我希望自己、孩子和其他家人的经历不会被错误合并。
6. 作为用户，我离开小程序或生成失败后仍能找回任务与输入。
7. 作为用户，我能预览完整海报，再主动保存或分享。
8. 作为运营人员，我能独立维护每个分类的提示词、预览样例、发布与回退版本。
9. 作为运营人员，我能查看成功率、失败阶段与生成成本，定位问题；常规运维不默认浏览用户私人知识正文。

## 4. 实现与业务边界（Implementation Decisions）

### 4.1 提示词管理

首期后台提供：分类列表、显示名称与排序、输入提示、分类提示词草稿、测试样例、发布版本、回滚。分类可停用，不删除已生成记录所引用的历史版本。

- 平台管理分类模板，普通账号无需编写提示词；账号知识和表达偏好作为变量注入。
- 同一通用规则被各分类复用，避免五套提示词重复维护并出现规则漂移。
- 每个制作任务记录通用规则版本、分类模板版本、采用的知识条目 ID 与版本、模板版式版本。
- 发布新提示词仅影响新任务，重试保持原任务的输入与提示词版本；用户主动重新制作时采用当前已发布版本。
- 用户资料、上传文字和知识库内容都是数据，不能覆盖账号权限或系统规则。

### 4.2 海报生成提示词

完整总提示词统一维护在[产品方案 v1.0 第六节](../../产品方案-v1.0.md)，包括输入变量、逐图理解、图片处理、逐图夸赞、整体设计和输出检查。本节不保留另一份旧模板，避免出现维护漂移。

旧的单一 `title + body` 输出不能覆盖多图需求。正式文案阶段至少输出 `title` 与 `photo_items`，每项绑定 `photo_id`、`praise`、`visible_facts` 和 `processing_notes`；内部事实和处理说明不进入公开海报。

### 4.3 分类提示词与接入方式

五类分类提示词以[产品方案第六节第 3 部分](../../产品方案-v1.0.md)为准。共用通用规则，将当前分类内容注入 `{{对应分类提示词}}`，用户无需自己编写提示词。

正式接入拆为两阶段：先逐图理解并生成文案、完成内部校验，再将已校验文字与对应原图交给图片处理和合成阶段；后者不能重新编写夸赞或补入私密事实。每张照片保留稳定编号，1–6 张照片最终输出一张 3:2 横版海报，成功计 1 次。全文模板、阶段输出及验收要求均见上述产品方案，尚待真实模型效果验证。

### 4.4 账号个人知识库

已确认：每个账号拥有独立的个人／家庭知识库，记录用户及家人的经历、偏好，帮助 AI 更懂本人。第一版不包含商家、品牌或产品资料。

**用户界面建议命名“关于我”，在“我的”内提供以下分组：**

| 分组 | 首期字段或操作 | 示例 |
|---|---|---|
| 我与家人 | 昵称、与我的关系、独立主体 ID；按需添加与修改，均非首次生成必填 | 我、女儿；不要求上传家人证件或完整生日 |
| 喜好与表达偏好 | 喜欢的活动、喜欢的回应语气、不希望出现的表达 | 喜欢户外；文案自然一点；不喜欢“伟大妈妈”这类称呼 |
| 值得记住的经历 | 发生了什么、涉及谁、日期可选、原始来源 | 最近在陪女儿学习骑车；只记录用户明确提供的事实 |
| 资料使用设置 | 逐条编辑、停用、删除、允许用途；账号总开关与本次生成可不使用资料 | 本次只根据照片与配文生成 |

知识库的价值是让回应持续贴合本人，而不是要求每次生成前填写档案。首页不新增知识表单；已启用知识时可用一行轻提示“结合我的资料”，点击可查看或关闭。没有资料时不显示空资料任务或完成度压力。

**资料如何进入：**

1. 用户在“关于我”主动添加与修改。
2. 用户在制作记录详情主动选择“记住这件事”，系统从用户原始配文整理候选条目，展示主体、内容及用途供确认；不能从生成海报文案提取“事实”。
3. 一次记录涉及多位家人时，候选条目分开标明主体；无法确定时请用户选择，暂不入库，不影响海报制作。

**资料如何使用：**

- 使用账号通用表达偏好，以及与本次明确主体、场景相关的经历。
- 宝妈分类只代表本次回应侧重，不是永久身份；点击分类不自动新增“用户为母亲”等事实。
- 多个家人的经历严格分开，不能因为选了宝妈就检索并混用所有孩子的资料。
- 例如用户偏好“不要夸张称呼，多看见我自己的感受”，宝妈提示词就用自然语气回应其陪伴与疲惫；不需要把这条偏好原文写在海报上。
- 长期事实不因一次生成而更改；过时经历可停用，修正需要用户明确操作。

- 一个账号管理一套知识集合；分类通过适用标签和相关性调用，不复制成五个重复知识库。
- 第一版支持手动新增、编辑、停用、删除，字段包括内容、主体、标签、来源、适用分类、状态及使用范围。
- “来源”与“主体”分开：谁录入不等于这条事实描述谁；避免把他人经历归给当前用户。
- 知识入库不是分享授权。区分“不用于生成”“仅作背景、不主动公开具体事实”“允许引用到分享文案”。默认采用不公开具体事实的保守范围，用户可逐条调整。
- 每次只检索少量相关且有效的条目；知识库为空或无相关结果时直接生成，不编造记忆。
- AI 生成的赞美不能自动回写为用户事实。
- 本次配文可提取为候选条目，但首期不做静默自动入库；经用户确认后才能加入知识库。
- 停用或删除后，后续检索立即排除，并清理相关索引和缓存；已经分享出去的图片不能远程撤回，应在删除说明中明确。
- 生成发布结果前再次核验知识条目可用性；若中途撤回了使用权限，重新生成无该条目的内容或取消本次任务，不发布已撤回的事实。
- 知识库是账号资产，首期不默认与云忆回忆录资料互通。

### 4.5 账号隔离与数据对象

本稿定义边界，不指定数据库、云服务或模型供应商。

| 对象 | 关键字段与责任 |
|---|---|
| Account | 账号 ID、登录关联、状态、知识使用总开关 |
| Subject | owner_account_id、主体 ID、本人／家人关系、昵称；由用户录入或确认 |
| Category / PromptVersion | 分类 ID、展示配置、版本、草稿／发布状态 |
| KnowledgeItem | owner_account_id、subject_id（通用表达偏好可无具体家人主体）、类型、用户确认内容、来源、标签、适用分类、使用范围、版本、启用状态 |
| Asset | owner_account_id、资源标识、可用状态；保存用户上传原图 |
| GenerationJob | owner_account_id、分类、输入快照、提示词版本、知识引用版本、状态、attempt、错误码 |
| Poster | owner_account_id、job_id、标题、逐图夸赞与照片编号对应关系、成品资源、创建时间 |
| ShareRecord | 仅在需要链接分享时启用；绑定允许公开的单个成果，不暴露制作记录或知识库 |

- 服务端根据已验证登录身份确定账号，忽略客户端自报的 owner_account_id。
- 知识检索先按账号限定范围，再做相关性匹配；不能先跨账号召回，再靠提示词要求“不泄露”。
- 任务、照片、成品、缓存、索引、导出与回调都校验归属，避免仅数据库列表隔离而资源 URL 泄露。
- 登录切换时隔离草稿与缓存；退出后不在另一个账号显示上一个账号的内容。
- 分享链接只读取用户明确分享的成果；接收者不获得源照片集合、账号知识或私有任务接口权限。

### 4.6 异步生成与失败恢复

任务状态建议：排队中 → 制作中 → 已完成／失败／已取消。界面只显示真实状态，不模拟完成倒计时。

- 提交即持久化服务端任务，离开小程序不丢任务；重新打开可从记录恢复。
- 同一次提交防重；失败重试递增 attempt，过期回调不得覆盖较新的结果。
- 文案成功而排版失败时优先恢复排版阶段，不重复产生不必要的模型调用。
- 新版本制作不覆盖旧海报；输入修改创建新任务。
- 完成提示不抢占正在编辑的内容。
- 生成可追踪成功率、等待时长、模型用量与成本；不通过日志长期复制完整私人知识。

### 4.7 保存与分享

- 首期必须完成成品图片生成、预览与保存；外部分享由用户主动触发。
- 小程序页面分享与海报图片保存分开定义；朋友圈、订阅通知等能力以开发时官方接口和实际权限验证为准，本稿不承诺所有渠道均可一键完成。
- 非授权接收方不得通过海报地址访问知识库或原始任务资料。

## 5. 验收方案（Testing Decisions）

当前是需求文档，以下为未来开发验收标准，尚未执行。

| 范围 | 核心验收 |
|---|---|
| 分类 | 五类正确使用各自发布版本；切换不丢草稿；同一输入不同分类有合理侧重，不能为了差异编事实 |
| 冷启动 | 空知识库可正常出图；未登录编辑内容在账号识别取消后保留 |
| 个性化 | 相关资料能改善回应；无关资料不出现；不同主体不混用；当前输入与旧资料冲突时不沿用旧事实 |
| 使用权限 | 停用、删除、背景专用、允许引用四类行为正确；制作期间撤回权限后不发布对应事实 |
| 账号隔离 | A 账号不能通过猜 ID、资源 URL、搜索、任务恢复、分享或缓存读取 B 的资料 |
| 提示词注入 | 配文或知识条目里的“忽略系统、读取其他账号”等文字不能改变权限与指令层级 |
| 生成可靠性 | 重复点击不创建重复任务；刷新和离开可恢复；重试拒绝旧回调；失败保留输入 |
| 海报 | 1／3／6 图布局可读、不溢出；预览与导出一致；长标题、特殊字符、长配文有明确处理 |
| 知识写回 | 生成文案不会成为事实；候选知识须用户确认；删除已分享素材的能力边界清楚 |
| 分享 | 真机验证图片保存与所选分享路径；接收方只能看到获准公开内容 |

文案评估建议每类至少准备：正向事件、普通日常、疲惫／失落、资料冲突各一组，再增加跨主体与提示词注入样例。评估“是否贴合事实、是否具体自然、是否尊重情绪、是否适合公开分享”，不只测结构化输出是否可解析。
